# JUM — Project Status

**Read this file first in any new session before doing anything else.** It exists specifically so work can resume cleanly after a context/window switch without re-deriving decisions already made.

## What JUM is

A one-to-one listening service (not therapy/counselling) — customers book a paid voice session with a dedicated listener. India-based (justuandme.in, owned on GoDaddy), currently a **personal pilot project**, expecting **under 50 customers/month**. Cost-consciousness at pilot scale has driven several infrastructure decisions below — don't default to "the more robust option" without checking whether it's actually justified at this traffic level.

Fully bilingual (English/Telugu), navy/gold brand identity, and covers the *entire* customer journey end to end: home page, booking with a real 5-minute client-side slot-hold simulation, payment (with dynamically-required method fields), confirmation, live-call screen with extension flow, feedback with a sustainability-donation flow, host panel, and four fully-written legal policies (Terms/Privacy/Disclaimer/Refund). **Everything in it is simulated client-side — no real payment, no real backend.** Its value now is as the **reference for exact copy, UX flow, and visual design** when building the real app. Read it before building any real page so the real version matches what was already designed and refined over many iterations, rather than re-deriving copy/flow from scratch.

## Architecture decisions (and why — don't re-litigate without new information)

- **Frontend + backend:** Next.js 16 (App Router, TypeScript, Tailwind), deployed to **Azure Static Web Apps, Free tier**. Upgrade to Standard ($9/mo) only when traffic actually justifies it — it's a plan toggle, not a redeploy.
- **Scheduled/background jobs** (slot-hold expiry, 24h/1h/10min reminders): **Azure Functions**, Consumption plan (timer triggers). Free-grant usage (1M executions/mo) comfortably covers pilot scale.
- **Database:** **Neon PostgreSQL**, free tier. Connected and live (see below).
- **Rejected, with reasons:**
  - *Hostinger shared "Unlimited" hosting* — confirmed directly by Hostinger support: no PostgreSQL, Node.js not always-on (no persistent process, so payment webhooks could be missed), limited SSH, no custom background daemons. Their own answer: use a VPS for always-on Node + Postgres.
  - *Hostinger VPS (KVM1, ~$6.49→$11.99/mo)* — technically fine, but more ops burden (self-managed patching/security/Postgres admin) than justified at <50 customers/month once Azure's free tier covered the same needs for less money and less maintenance.
  - *Vercel Hobby (free)* — ruled out because its own terms restrict it to non-commercial use, and JUM charges real money even as a pilot. Vercel Pro ($20/mo) would be fine but is the most expensive option compared.
  - *Railway (~$5–10/mo)* — a reasonable option, but Azure ended up both cheaper (~$9/mo total) and better suited once the Functions timer-trigger pattern was matched to the reminder/hold-expiry need specifically.
- **Payment gateway:** Razorpay (not yet integrated — Phase 4). Chosen for UPI + India-native support and built-in PCI compliance.
- **Video/audio calling:** Daily.co (not yet integrated — Phase 6). Note: Twilio discontinued its video product in 2024, so it's SMS/WhatsApp-only in this stack, not video.
- **SMS/WhatsApp:** Twilio. **Email:** Resend. (Both Phase 5, not yet integrated.)

## Security & privacy review

A systematic read-through of every auth/payment/PII-relevant path (not a formal external audit) — done between Phase 7 and the still-pending Azure deploy. One fix applied immediately since it was risk-free; the rest are flagged for the user to weigh in on before real traffic hits this.

**Checked and solid — no changes needed:**
- Both Razorpay signature paths (`verifyPaymentSignature`, `verifyWebhookSignature` in `lib/razorpay.ts`) use `crypto.timingSafeEqual` and the server's own recorded `order_id`, never a client-supplied one, for the HMAC input.
- Admin passwords: scrypt with a per-admin salt, timing-safe hash comparison, and a dummy-hash path on login so a nonexistent email takes about as long as a wrong password (no email-enumeration timing leak).
- Session cookies: `HttpOnly` + `SameSite=Lax` + `Secure` in production, HMAC-signed, 12h expiry.
- Prisma ORM everywhere — no hand-built SQL, so no SQL-injection surface.
- Every `dangerouslySetInnerHTML` call renders only our own static i18n copy, never user input (checked all three call sites: legal pages, booking-form consent text).
- `.env` has never been committed — checked the *entire* git history (`git log --all -p -- .env`), not just the current tree.
- `npm audit` reports 0 known vulnerabilities in dependencies.
- The public `GET /api/bookings/:id` endpoint returns a hand-picked field subset (no email/phone/notes), and hides the call code until the booking is actually `CONFIRMED`.
- Booking price is always server-computed from `DURATION_PRICING_INR`, never trusted from client input — no price-tampering vector.

**Fixed during this review:**
- `x-admin-key` comparison used plain `!==` (not timing-safe) while every other secret comparison in the codebase used `crypto.timingSafeEqual` — inconsistent, and a timing side-channel in principle. Now uses the same timing-safe helper. Verified: correct key still works, wrong key and different-length key are both still rejected.
- **Rate limiting added** (`lib/rateLimit.ts`) — DB-backed sliding window (new `RateLimitHit` model; deliberately not in-memory, since serverless/hybrid hosting can run multiple instances that wouldn't share in-memory state), opportunistically self-cleaning old rows on each check rather than needing a separate job. Applied to `POST /api/bookings` (5 per 10 min per IP — stops calendar-griefing, still allows a genuine customer a few retries) and `POST /api/admin/login` (5 per 15 min per IP — brute-force defense-in-depth). Live-tested against the real dev server: both correctly allow the first 5 requests and 429 the 6th/7th.
- **`POST /api/bookings/:id/confirm` removed entirely** (not just restricted) — no real usage existed (frontend uses the verify/webhook paths; test scripts call `confirmBooking()` as a direct lib import, not over HTTP), so removing it was pure attack-surface reduction with no functionality lost. The underlying `confirmBooking()` function stays in `lib/bookings.ts` for test scripts, just isn't reachable over HTTP anymore. Verified the route now 404s.
- All 61 existing regression checks (availability/bookings/payments) re-run clean after these changes.

**Still flagged, not yet fixed — needs a decision, not urgent at pilot scale but worth doing before real traffic:**
1. **No email verification on booking creation.** `createBookingRequest` does find-or-create by email with no confirmation step, so someone could submit (and the admin would see) a booking under another person's real email address. Low harm today (no notifications exist yet — Phase 5), but worth closing when Phase 5 adds email, e.g. requiring a confirmation click before a request reaches the pending queue.
2. **No max-length validation** on `notes`, `displayName`, or `phone` — unbounded text storage, low severity at this scale.
3. **No CSRF token** on state-changing admin routes (login/logout/approve/decline) — `SameSite=Lax` covers most of this in current browsers, but it's not defense-in-depth.
4. **No security headers configured** (CSP, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, HSTS) in `next.config.ts` — worth checking what Azure SWA adds by default post-deploy before deciding whether to add more.
5. **GitHub repo visibility unconfirmed from this session** — no secrets are in the repo (verified above), but if `github.com/justuandmejum/JUM` is public, the exact pricing/auth/business logic is too. Worth the user double-checking it's set to what they actually intend.

## Important gotchas learned this session (do not rediscover these the hard way)

- **This machine had no Node.js installed.** Installed via `winget install OpenJS.NodeJS.LTS`. It's at `C:\Program Files\nodejs`. **The PATH is now set correctly and permanently** (User env var) — but if a *new terminal session* still can't find `node`/`npm`, that's just because the shell process predates the PATH fix; open a genuinely fresh terminal.
- **Next.js 16 has real breaking changes from typical training-data knowledge.** Before writing Next.js code in a fresh session, read `jum-app/node_modules/next/dist/docs/` directly (especially `01-app/01-getting-started/08-caching.md` and `01-app/03-api-reference/03-file-conventions/route.md`) rather than assuming prior knowledge is current. Key points already confirmed: route handler `params` is a `Promise` (must `await`); the new "Cache Components" (`cacheComponents: true` in `next.config.ts`) is a major opt-in paradigm shift and is **currently OFF** — this project uses the familiar previous caching model, so mark dynamic routes explicitly with `export const dynamic = 'force-dynamic'` (booking/webhook endpoints will need this).
- **Prisma 7 also has breaking changes:**
  - Generator is `provider = "prisma-client"` (not `prisma-client-js`), output path is explicit (`app/generated/prisma`), and **that generated folder has no `index.ts`** — import from the file directly: `from "../app/generated/prisma/client"`, not the bare directory.
  - `PrismaClient` **requires an explicit driver adapter** — it no longer reads `DATABASE_URL` implicitly. See `lib/prisma.ts` for the working pattern (`@prisma/adapter-pg` + `PrismaPg`).
  - DB connection URL lives in `prisma.config.ts` (via `dotenv`), not directly in `schema.prisma`'s datasource block.
  - Standalone scripts (outside Next's own dev server) don't auto-load `.env` — run them with `npx tsx -r dotenv/config <script>`.
- **`.env` contains the real Neon connection string already** (gitignored, not committed — `.env.example` is the tracked template). No need to re-ask the user for it in a fresh session; just confirm `jum-app/.env` still exists and has a valid `DATABASE_URL`. It now also has `ADMIN_API_KEY` (generated Phase 3, real random value already in place).
- **Postgres won't let a newly added enum value be used in the same transaction that added it.** Adding `PENDING_APPROVAL` to `BookingStatus` and then referencing it in the partial unique index's `WHERE` clause had to be two separate migrations (run via two separate `prisma migrate dev` invocations), not one hand-edited file — combining them fails. Also: after hand-writing a migration folder (rather than letting `prisma migrate dev` generate it), remember to run `npx prisma generate` — `migrate dev` regenerates the client for migrations *it* creates, but picked up our hand-written folder as "apply pending migrations" and skipped regen, leaving the client stale until generated explicitly.
- **`prisma.config.ts`'s `dotenv/config` import doesn't reach plain `node -e` one-liners or `.mjs` files run outside `tsx`** — stick to `npx tsx -r dotenv/config <script>.ts` for one-off DB scripts, same as the existing test scripts, rather than improvising inline `node -e`.
- The `jum-app` folder name was deliberate — the parent folder `chandu jum` has a space in it, which breaks npm package naming, hence scaffolding into a subfolder.
- **Azure Static Web Apps hybrid Next.js support (SSR + API routes) works on the Free plan** — a managed backend is automatic on every plan; Standard+ is only needed if you later want a *custom/linked* backend for extra performance, not for basic hybrid rendering to work at all. Confirmed via Microsoft Learn (`deploy-nextjs-hybrid`), not assumed. Still in **preview** as of this doc. Notable constraints: 250MB max app size (irrelevant at our scale unless something balloons `node_modules`), no SWA CLI local emulation/deployment for hybrid apps (must deploy via the GitHub Actions workflow Azure generates, not the CLI), and if custom `middleware.ts` or `next.config.ts` redirects/rewrites are ever added, they must explicitly exclude `.swa` paths or Azure's own deployment health check (`/.swa/health.html`) breaks — not a concern yet since neither exists in this app.
- **Both Razorpay and Azure need real accounts only the user can create** — signing up for either is outside what Claude can do (financial/account-creation actions require the user directly). Test-mode Razorpay keys are available immediately post-signup, before KYC clears, so that doesn't have to fully block Phase 4.
- **Extracting embedded base64 assets or large JS data objects from the prototype HTML**: don't read them into context directly (the prototype's embedded logo/hero images made single lines 700KB–1.9MB, blowing past tool read limits). Write a small Node script that reads the file, regexes out the `data:...;base64,...` payload or runs the relevant JS snippet in `node:vm`, and writes the result straight to a file — the extraction script for this session's `I18N` dictionary (`vm.runInContext`) turned ~230 lines of prototype JS into two clean JSON files without ever printing the Telugu text through a lossy transcription step.
- **The Browser pane's `computer` tool (coordinate/ref-based clicks) didn't reliably land on real elements in this session** — the pane wasn't visually composited (`screenshot` failed with "pane is not displayed"), and clicks that referenced valid refs silently missed. Driving the same interactions via `javascript_tool` (`element.click()`, dispatching real `input`/`change` events with native property setters so React's controlled inputs pick them up) worked reliably instead — still exercises real DOM event handlers, just doesn't depend on the pane being rendered.
- **React 19 Strict Mode double-invokes effects in dev** — the payment-order-creation effect fired twice on one page load during testing. This is expected dev-only behavior, not a bug, *as long as the effect is idempotent* — `initiatePayment()` already was (reuses the existing pending order rather than creating a duplicate), so no fix was needed. Worth checking idempotency rather than assuming a double network call is a bug.
- **Razorpay's actual documented domestic test card is `4100 2800 0000 1007`** (Visa) — the generic industry-standard test number `4111 1111 1111 1111` that gets cited everywhere is rejected by Razorpay specifically as an "international card." Any future date + random CVV + random 4–10 digit OTP if asked. Full list (Mastercard/RuPay/Diners/Amex) is in this session's transcript if needed.
- **UPI can't be meaningfully tested against a real phone in Razorpay test mode** — intent/QR flows require the live NPCI network, which test-mode transactions aren't on. Use the card flow above for testing instead. Also: NPCI deprecated UPI Collect (manual UPI-ID entry) platform-wide as of 28 February 2026 — it's gone for everyone, not a config option we removed or could restore.
- **Razorpay refund *creation* can be blocked by account KYC status even when order creation and payment capture both work fine** — confirmed by getting a `400 "invalid request sent"` on `POST /v1/payments/:id/refund` against a genuinely captured payment (3 different valid request-body shapes, identical failure) while `GET` on the sibling refunds-*list* endpoint for the same payment succeeded. If a future session hits this again, check account KYC/activation status before assuming the request is malformed.
- **A gateway call failing inside a lib function should never bubble up as a raw 500** — when `applyRefund()`'s Razorpay call failed, it surfaced as an unhandled exception until wrapped in a try/catch that re-throws as the domain's own error type (`BookingError`). The existing route-handler pattern (`if (err instanceof BookingError) return Response.json(...)`) only helps if the lib layer actually throws that type — worth checking for this pattern anywhere else a lib function calls an external API and could fail.
